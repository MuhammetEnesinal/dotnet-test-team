# Final report (at most 25 lines, the user's language)

1. **Possible code bugs first.** If none: "no code bug found within the tested scope; N scenarios were not tested", never just "no bug". For each: input, expected and why (basis), actual, `file:line`, proposed fix. Production code was not changed. Say "possible" unless the classifier or the evidence is clear; say what decides it.
2. **Counts** that agree with `03-round-<n>.md` and the test results: scenarios approved / implemented / skipped (reasons); tests passing / failing (why failing tests stay). Failing tests that prove a bug turn the user's CI red once committed: ask whether to keep them failing or list them. Never skip or comment them out.
3. **With a request:** "N scenarios -> M test methods" and a line "Not covered because of your request" (`scope.leftOut`, `exclude`); say "within the requested scope" instead of a general all-clear.
4. **What ran:** the `dtt run` result lines (build, tests, flaky, and the `production:` line; `production: not checked` or `CHANGED` is a problem to report, never to ignore), the integrity gate, the environment used (SDK, framework, runner, stack), and anything not run and why. Database fidelity notes: which database the tests used (real container of the project's kind with engine and tag, SQLite, helper, mocks), what a stand-in could not test (row version/concurrency, filtered indexes, decimal ordering...), whether the container was removed or kept (and the command to delete it), and whether the plugin downloaded the image (the `docker rmi <image>` line to free the space). Controller filters/routing/model binding are not covered.
5. **Open questions**, and where the run folder is (`.test-generator/runs/<id>`) and how to resume or delete it.
